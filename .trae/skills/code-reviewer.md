# 代码审查技能 (Code Reviewer)

## 何时使用（When）

当需要对以下情况进行代码审查时使用此技能：
- 新功能开发完成后的代码审查
- Bug 修复后的代码审查
- 重构后的代码审查
- Pull Request / Merge Request 审查
- 定期代码质量检查
- 用户明确要求进行 code review 时

**不要在以下情况使用**：
- 只是生成代码，不需要审查时
- 简单的格式调整
- 用户只是询问代码逻辑时

---

## 如何执行（How）

### 审查流程

按照以下顺序进行全面审查：

#### 1. 规范遵循检查
- [ ] 代码是否符合 `.trae/rules/typescript-style.md` 中的命名规范
- [ ] 代码是否符合 `.trae/rules/backend/api-design.md` 中的分层架构
- [ ] 类型注解是否完整，是否使用了 `any`
- [ ] 函数参数和返回类型是否明确
- [ ] 代码格式是否符合 Prettier 规范

#### 2. 逻辑正确性检查
- [ ] 业务逻辑是否正确实现了需求
- [ ] 边界条件是否处理（空值、零值、最大值等）
- [ ] 错误处理是否完善（try/catch、错误类型）
- [ ] 异步操作是否正确处理（async/await、Promise）
- [ ] 状态流转是否符合业务规则

#### 3. 潜在 Bug 检查
- [ ] 是否有空指针/undefined 访问风险
- [ ] 数组越界问题
- [ ] 类型转换是否安全
- [ ] 并发/竞态条件问题
- [ ] 内存泄漏风险
- [ ] 无限循环风险

#### 4. 性能问题检查
- [ ] 是否有 O(n²) 或更高复杂度的算法
- [ ] 循环中是否有不必要的计算
- [ ] 是否有重复计算可以缓存
- [ ] 数据库查询是否可能有 N+1 问题
- [ ] 大列表是否有分页

#### 5. 安全问题检查
- [ ] 用户输入是否经过验证
- [ ] SQL 注入风险
- [ ] XSS 攻击风险
- [ ] 敏感信息是否泄露（日志、错误信息）
- [ ] 认证授权检查是否到位
- [ ] CORS 配置是否安全

#### 6. 可维护性检查
- [ ] 函数是否过长（超过 30 行）
- [ ] 嵌套是否过深（超过 3 层）
- [ ] 是否有重复代码
- [ ] 命名是否清晰表达意图
- [ ] 注释是否充分（复杂逻辑有说明）
- [ ] 模块职责是否单一

#### 7. 测试覆盖检查
- [ ] 新代码是否有对应的单元测试
- [ ] 测试是否覆盖了主要分支
- [ ] 是否有边界条件测试
- [ ] 是否有异常场景测试

### 输出格式

审查结果按照以下格式输出：

```
## 代码审查报告

**审查文件**: [文件名]
**审查时间**: [时间]
**总体评价**: [优秀/良好/一般/需改进]
**严重问题数**: N
**建议改进数**: N

---

### 🔴 严重问题 (必须修复)

1. **问题标题**
   - 位置: [文件:行号]
   - 问题描述: [详细描述]
   - 风险等级: 高/中/低
   - 修复建议: [具体建议]
   - 代码示例:
     ```typescript
     // 修复前
     // ...
     
     // 修复后
     // ...
     ```

### 🟡 建议改进 (建议修复)

1. **改进点标题**
   - 位置: [文件:行号]
   - 改进描述: [详细描述]
   - 改进理由: [为什么要改]
   - 改进建议: [具体建议]

### ✅ 做得好的地方

- [具体的优点]

---

### 总结

[总体评价和建议]
```

---

## 产出什么（What）

产出一份结构化的代码审查报告，包含：
1. 总体评价（等级、问题数量统计）
2. 严重问题列表（必须修复的 Bug、安全漏洞等）
3. 建议改进列表（代码质量、可维护性改进）
4. 做得好的地方（正向反馈）
5. 总结和下一步建议

### 审查标准

- **优秀**：代码质量高，无明显问题，可直接合并
- **良好**：有少量建议改进项，无严重问题，修复后可合并
- **一般**：有 1-2 个严重问题或多个改进项，需要修复后重新审查
- **需改进**：有多个严重问题或架构问题，需要较大修改
